# NET-04 · Статическая маршрутизация

> Обеспечить двустороннюю связь между удалёнными подсетями через явные маршруты.

| Формат | Исходный кейс | Основной фокус |
| :-- | :-- | :-- |
| Учебная практика | `814` | Сети |

## Стенд и схема

Debian и сетевые ВМ по схеме кейса. Адреса и имена интерфейсов в командах — примеры, их нужно сверить с фактической схемой.

```mermaid
flowchart LR
    n0["Debian A / сеть A"]
    n1["Router A"]
    n2["Router B"]
    n3["Debian B / сеть B"]
    n0 --> n1 --> n2 --> n3
```

Схема показывает логику лабораторной. Для точного повторения исходного кейса используются его адресный план, образы и версии компонентов. Подготовка среды описана в [руководстве по стендам](../../../docs/lab-environment.md).

## Ход работы

1. Составить таблицу локальных и транзитных подсетей.
2. Настроить адреса интерфейсов и next hop на маршрутизаторах.
3. Добавить прямые и обратные маршруты, проверить firewall.
4. Проверить каждый участок пути отдельно и сравнить маршрут с ожидаемой схемой.

## Команды и контрольные проверки

```routeros
/ip address print
/ip route print detail
/ping 192.168.2.10 count=3
```

Это команды проверки или пример исправления, а не сохранённый вывод с выполненного стенда. Полный набор действий зависит от подготовленного образа и версии ПО.

## Как подтвердить результат

- Таблица destination / gateway для каждого маршрутизатора.
- Проверка связи между конечными узлами и описание обратного пути.

Для фиксации фактического прогона используется [шаблон отчёта](../../../templates/run-report.md).

## Что важно для SOC

Односторонняя связь часто связана с отсутствием обратного маршрута или политикой фильтрации. Сначала проверять путь, затем приложение.

## Защита и повторная проверка

Изменять маршруты по согласованному плану, документировать next hop и не открывать лишний межсегментный доступ.

После изменения конфигурации повторяется исходная проверка: нужно подтвердить устранение причины и сохранение штатной функции, а не только исчезновение ошибки в интерфейсе.
