# NET-03 · Динамическая адресация DHCP

> Проследить получение сетевых параметров от DHCP-сервера.

| Формат | Исходный кейс | Основной фокус |
| :-- | :-- | :-- |
| Учебная практика | `813` | Сети |

## Стенд и схема

Debian и сетевые ВМ по схеме кейса. Адреса и имена интерфейсов в командах — примеры, их нужно сверить с фактической схемой.

```mermaid
flowchart LR
    n0["DHCP-клиент"]
    n1["MikroTik / DHCP"]
    n2["Пул и аренды"]
    n0 --> n1 --> n2
```

Схема показывает логику лабораторной. Для точного повторения исходного кейса используются его адресный план, образы и версии компонентов. Подготовка среды описана в [руководстве по стендам](../../../docs/lab-environment.md).

## Ход работы

1. Подготовить MikroTik как DHCP-сервер и Debian как клиент.
2. Задать пул, шлюз, DNS и время аренды без пересечения с адресами инфраструктуры.
3. Обновить аренду средствами используемого сетевого менеджера.
4. В захвате трафика разобрать Discover, Offer, Request и ACK, сопоставить адрес клиента с арендой на сервере.

## Команды и контрольные проверки

```routeros
/ip dhcp-server print
/ip dhcp-server network print
/ip dhcp-server lease print
```

Это команды проверки или пример исправления, а не сохранённый вывод с выполненного стенда. Полный набор действий зависит от подготовленного образа и версии ПО.

## Как подтвердить результат

- Параметры пула и активная аренда клиента.
- Фрагмент DORA в PCAP с временными метками.

Для фиксации фактического прогона используется [шаблон отчёта](../../../templates/run-report.md).

## Что важно для SOC

Несколько Offer от разных серверов, неожиданный шлюз и быстрое исчерпание пула требуют проверки. Одна повторная выдача аренды не является атакой.

## Защита и повторная проверка

Использовать DHCP snooping при поддержке коммутатором, доверенные порты и мониторинг выдачи адресов.

После изменения конфигурации повторяется исходная проверка: нужно подтвердить устранение причины и сохранение штатной функции, а не только исчезновение ошибки в интерфейсе.
