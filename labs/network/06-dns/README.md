# NET-06 · DNS и разрешение имён

> Проверить разрешение доменных имён и отделить DNS-проблему от отсутствия сетевой связности.

| Формат | Исходный кейс | Основной фокус |
| :-- | :-- | :-- |
| Учебная практика | `746` | Сети |

## Стенд и схема

Debian и сетевые ВМ по схеме кейса. Адреса и имена интерфейсов в командах — примеры, их нужно сверить с фактической схемой.

```mermaid
flowchart LR
    n0["Клиент"]
    n1["DNS на MikroTik"]
    n2["Ответ или NXDOMAIN"]
    n0 --> n1 --> n2
```

Схема показывает логику лабораторной. Для точного повторения исходного кейса используются его адресный план, образы и версии компонентов. Подготовка среды описана в [руководстве по стендам](../../../docs/lab-environment.md).

## Ход работы

1. Указать DNS-сервер в конфигурации клиента и маршрутизатора.
2. Создать учебную запись и проверить ответ от нужного сервера.
3. Сравнить ответы для существующего и отсутствующего имени.
4. Зафиксировать запрос, ответ, TTL и код результата; проверить влияние кеша.

## Команды и контрольные проверки

```bash
cat /etc/resolv.conf
getent hosts example.com
dig @192.168.1.1 lab.example.test A
dig @192.168.1.1 absent.example.test A
```

Это команды проверки или пример исправления, а не сохранённый вывод с выполненного стенда. Полный набор действий зависит от подготовленного образа и версии ПО.

## Как подтвердить результат

- Запросы и ответы DNS с указанием использованного сервера.
- Сравнение NXDOMAIN, таймаута и успешного ответа.

Для фиксации фактического прогона используется [шаблон отчёта](../../../templates/run-report.md).

## Что важно для SOC

Массовые NXDOMAIN, смена DNS-сервера или необычные домены требуют контекста. Кеширование и фоновые запросы ОС могут объяснять часть активности.

## Защита и повторная проверка

Ограничивать рекурсию доверенными клиентами и отслеживать изменения DNS-настроек.

После изменения конфигурации повторяется исходная проверка: нужно подтвердить устранение причины и сохранение штатной функции, а не только исчезновение ошибки в интерфейсе.
