# NET-14 · UDP-сканирование

> Корректно интерпретировать ответы и отсутствие ответов UDP-сервисов.

| Формат | Исходный кейс | Основной фокус |
| :-- | :-- | :-- |
| Учебная практика PT Start | `821` | Сети |

## Стенд и схема

Debian и сетевые ВМ по схеме кейса. Адреса и имена интерфейсов в командах — примеры, их нужно сверить с фактической схемой.

## Ход работы

1. Выбрать один учебный хост с известным UDP-сервисом.
2. Проверить небольшой заданный набор портов.
3. Сопоставить результат с настройками сервиса и захватом трафика.
4. Отдельно объяснить open, closed и open
5. filtered; не считать молчание подтверждением открытого порта.

## Команды и контрольные проверки

```bash
sudo nmap -sU -p 53,123,161 --reason 192.168.1.10
```

Это команды проверки или пример исправления, а не сохранённый вывод с выполненного стенда. Полный набор действий зависит от подготовленного образа и версии ПО.

## Как подтвердить результат

- Вывод проверки с причиной состояния порта.
- UDP-ответ или ICMP-ошибка, время и адреса обмена.

Для фиксации фактического прогона используется [шаблон отчёта](../../../templates/run-report.md).

## Что важно для SOC

Обход многих UDP-портов одного узла и ICMP Port Unreachable помогают заметить сканирование. Rate limiting может искажать результат.

## Защита и повторная проверка

Ограничивать доступ к UDP-сервисам нужными сегментами, отключать ненужные службы и проверять правила фильтрации.

После изменения конфигурации повторяется исходная проверка: нужно подтвердить устранение причины и сохранение штатной функции, а не только исчезновение ошибки в интерфейсе.
