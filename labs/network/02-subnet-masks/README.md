# NET-02 · Маски подсетей и VLSM

> Подобрать маски под число хостов и проверить границы широковещательных доменов.

| Формат | Исходный кейс | Основной фокус |
| :-- | :-- | :-- |
| Учебная практика | `812` | Сети |

## Стенд и схема

Debian и сетевые ВМ по схеме кейса. Адреса и имена интерфейсов в командах — примеры, их нужно сверить с фактической схемой.

```mermaid
flowchart LR
    n0["План адресов"]
    n1["Подсети VLSM"]
    n2["Проверка маршрутов"]
    n0 --> n1 --> n2
```

Схема показывает логику лабораторной. Для точного повторения исходного кейса используются его адресный план, образы и версии компонентов. Подготовка среды описана в [руководстве по стендам](../../../docs/lab-environment.md).

## Ход работы

1. Выписать потребность каждого сегмента в адресах и отсортировать сегменты по размеру.
2. Рассчитать адрес сети, допустимый диапазон хостов и broadcast.
3. Назначить адреса на учебном стенде и проверить связь внутри и между сегментами.
4. Объяснить, почему неверная маска меняет выбор между ARP и отправкой через шлюз.

## Команды и контрольные проверки

```bash
python3 - <<'PY'
from ipaddress import ip_network
for cidr in ['192.168.10.0/26', '192.168.10.64/27']:
    net = ip_network(cidr)
    hosts = list(net.hosts())
    print(net, hosts[0], hosts[-1], net.broadcast_address)
PY
```

Это команды проверки или пример исправления, а не сохранённый вывод с выполненного стенда. Полный набор действий зависит от подготовленного образа и версии ПО.

## Как подтвердить результат

- Таблица VLSM: сегмент, CIDR, первый/последний хост, broadcast.
- Схема непересекающихся диапазонов и проверки достижимости.

Для фиксации фактического прогона используется [шаблон отчёта](../../../templates/run-report.md).

## Что важно для SOC

Ошибочная маска может выглядеть как частичная потеря связи. При расследовании сопоставлять адреса, маршруты и фактический L2-сегмент.

## Защита и повторная проверка

Проверять пересечения диапазонов и резервировать адреса инфраструктуры в едином адресном плане.

После изменения конфигурации повторяется исходная проверка: нужно подтвердить устранение причины и сохранение штатной функции, а не только исчезновение ошибки в интерфейсе.
