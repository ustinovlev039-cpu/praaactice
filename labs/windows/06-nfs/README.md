# WIN-06 · NFS между Linux и Windows

> Проверить сетевой доступ к каталогу и соответствие разрешений на двух ОС.

| Формат | Исходный кейс | Основной фокус |
| :-- | :-- | :-- |
| Учебная практика PT Start | `852` | Windows |

## Стенд и схема

Windows/Windows Server с нужными ролями; для доменных команд — RSAT/модуль ActiveDirectory или GroupPolicy. Повышенная консоль нужна только для административных шагов.


Схема показывает логику лабораторной. Для точного повторения исходного кейса используются его адресный план, образы и версии компонентов. Подготовка среды описана в [руководстве по стендам](../../../docs/lab-environment.md).

## Ход работы

1. Подготовить NFS-сервер и Windows-клиент с поддержкой нужного компонента.
2. Создать отдельный экспорт с доступом только из лабораторной подсети.
3. Подключить ресурс с Windows и проверить чтение/запись тестового файла.
4. Сопоставить доступ с UID/GID и настройками экспорта; отключить ресурс после проверки.

## Команды и контрольные проверки

```bash
exportfs -v
showmount -e 192.168.56.20
# Выполнять на NFS-сервере или Linux-клиенте с nfs-common.
```

Это команды проверки или пример исправления, а не сохранённый вывод с выполненного стенда. Полный набор действий зависит от подготовленного образа и версии ПО.

## Как подтвердить результат

- Настройки экспорта и таблица разрешений.
- Результат доступа с Windows и обезличенные серверные события.

Для фиксации фактического прогона используется [шаблон отчёта](../../../templates/run-report.md).

## Что важно для SOC

Версия NFS и схема идентификации влияют на модель доступа. Нельзя переносить предположения о NTFS/SMB-правах на NFS без проверки.

## Защита и повторная проверка

Ограничивать экспорт адресами и правами, не делать общий writable-экспорт и проверять необходимость anonymous mapping.

После изменения конфигурации повторяется исходная проверка: нужно подтвердить устранение причины и сохранение штатной функции, а не только исчезновение ошибки в интерфейсе.
