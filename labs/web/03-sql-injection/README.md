# WEB-03 · SQL Injection

> Выявить небезопасную сборку SQL и проверить исправление параметризованным запросом.

| Формат | Исходный кейс | Основной фокус |

**Привязка к OWASP:** A05:2025 Injection.

## Стенд и схема

Учебное приложение и компоненты соответствующего кейса PT Start. URL, параметры и пути необходимо брать из своего стенда; примеры ниже поясняют проверку или исправление.

## Ход работы

1. Сохранить обычный запрос к учебному приложению и набор возвращаемых тестовых данных.
2. Изменить один параметр в Burp Repeater и сравнить реакцию на границу строкового значения.
3. Проверить управляемое изменение логики выборки на синтетических данных стенда.
4. Разобрать место сборки SQL и заменить конкатенацию параметризацией.
5. Повторить ту же проверку и убедиться, что ввод обрабатывается как данные.

## Команды и контрольные проверки

```python
# Пример исправления для sqlite3; адаптировать под драйвер проекта.
row = connection.execute(
    'SELECT id, name FROM users WHERE name = ?', (user_input,)
).fetchone()
```

Это команды проверки или пример исправления, а не сохранённый вывод с выполненного стенда. Полный набор действий зависит от подготовленного образа и версии ПО.

## Как подтвердить результат

- Исходный и изменённый запросы, ответ и фрагмент уязвимой/исправленной обработки.
- Регрессионная проверка с тем же вводом на тестовых данных.

Для фиксации фактического прогона используется [шаблон отчёта](../../../templates/run-report.md).

## Что важно для SOC

Один ответ 500 не подтверждает SQLi. Сопоставлять различия результатов, ошибки СУБД и обработку параметра; не путать валидную бизнес-фильтрацию с внедрением.

## Защита и повторная проверка

Использовать параметризованные запросы, минимальные права БД и безопасную обработку ошибок.

После изменения конфигурации повторяется исходная проверка: нужно подтвердить устранение причины и сохранение штатной функции, а не только исчезновение ошибки в интерфейсе.
